# Crux PE13 Actions builds and ZIP releases

- This checkout owns the `aosp_crux-userdebug` cloud build, its verification and its signed TWRP ZIP release. Start with the [repository README](README.md) and the [standard-runner acceptance and rerun guide](docs/standard-runner-rom-build-acceptance-2026-11-05.md). The local OrbStack build compiles the same pinned code and packages the same ZIP with `scripts/crux_zip.py` and `installer/`; it never publishes here.
- Use public-repository standard GitHub-hosted `ubuntu-22.04` runners under the GitHub Free plan: no larger or self-hosted runners and no paid usage. Private inputs come only from the two pinned GitHub snapshot repositories through `CRUX_SOURCE_SNAPSHOTS_TOKEN`; build artifacts, logs and releases in this repository are public. The admitted graph summary, index receipt and pack registry under `docs/evidence/` are consumed build inputs. If inputs expire, use the [freeze and prepare procedure](docs/standard-runner-freeze.md) and review the new admission records; changing a workflow run ID alone is insufficient. Preserve same-run shard receipts and the paired kernel, DTBs, overlay, ramdisks and symbols.
- Pass the successful cold compile run as `build_run` to [assemble-standard.yml](.github/workflows/assemble-standard.yml); the assembly verifies the four images and both FITs and adds the unsigned ZIP payload under `zip-payload/`. Pass the matching successful assembly run as `assembly_run` to [release.yml](.github/workflows/release.yml) with the offline signature of that payload's `crux-install.txt`. Do not manually upload or repackage accepted ROM images or use local outputs as inputs.
- Sign offline with `scripts/crux_zip.py sign` and the install key; keep the private key out of every repository, Actions secret and synced note. `keys/crux-b-install-2026-11-07.pub.pem` verifies the signature, and `config/install-twrp.json` pins the RAM-only install TWRP that every release carries.
- Remote dispatch requires authorization. Preflight does not mutate Releases; draft and publish are separately authorized writes and stay separate from device installation.
- Before a local build, run `scripts/check_local_source.py` against the VM source tree: the local build is the same code only when it reports no problems.
- For code changes, run the relevant unittest subset from this checkout, for example `python3 -m unittest tests.test_crux_zip tests.test_release_zip tests.test_release_source` for packaging and release, and `make -C installer test` for the installer. Broaden to `python3 -m unittest discover -s tests` for shared pipeline changes and use `actionlint` for workflow changes. Hosted build, release and device acceptance are separate checks.
